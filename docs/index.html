Outbox Relay

How rest-service, Postgres, Kafka Connect, Kafka, and email-service hand an order off to a confirmation email — without ever calling each other directly.

An order is created by one HTTP request to rest-service and confirmed by an email sent from an entirely different process, email-service, minutes or seconds later. The two never open a connection to each other. rest-service writes to Postgres; Debezium tails Postgres's write-ahead log and republishes to Kafka; email-service only ever talks to Kafka. Postgres and Kafka are the whole interface between the two services.

primary data flow — HTTP → Postgres write → CDC → Kafka → consume protective control — idempotency lock, rate limiter trace propagation — W3C traceparent, outbox row → Kafka header → consumer span
  • rest-service and email-service share no network call, client, or API contract — the outbox table and the outbox.event.order topic are the entire interface between them.
  • The Redis lock and the Postgres write are independent failure domains: losing Redis loses deduplication of a replayed Idempotency-Key, not the correctness of the Order/outbox write itself.
  • The HTTP request's trace survives the CDC hop by riding inside the outbox row as a plain trace_context column, becoming a Kafka header only when Debezium's transform writes it — there is no shared request context between the two JVMs.
